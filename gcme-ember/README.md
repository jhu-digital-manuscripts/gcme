# gcme-ember

The Ember single-page application that powers the public UI of the Glossarial
Concordance to Middle English at <https://middleenglish.library.jhu.edu/>.

This package is built on Ember 6.12 LTS using Octane idioms (native classes,
`@tracked`, Glimmer components, angle-bracket invocation) and the browser-native
`fetch` API. At runtime it consumes the static JSON files generated by
`gcme-tool` (`group-title.json`, `tag-table.json`, `text-powersel.json`).

Searches are answered by one of two interchangeable backends, selected at build
time by `ENV.gcme.searchBackend` in `config/environment.js`:

- **`localsearch` (the default)** answers every search in the browser from the
  static JSON data files, so no search server is needed.
- **`opensearch`** sends queries to the OpenSearch endpoint configured by
  `ENV.gcme.opensearch` (the `/es` proxy in production, an absolute URL such as
  `http://localhost:9200/_search` in development).

See [Search backends](#search-backends) for the tradeoffs and configuration.

## Prerequisites

- **Node.js `>= 20.0.0 < 21.0.0`** is required to install, build, and test this
  package. The `engines.node` field in `package.json` enforces the range, and
  `npm install` will fail with an `EBADENGINE` error on any other version.
- npm 10.x (ships with Node 20).
- The generated data files in `public/`. They are created by by running
 n`./gen_data.sh` from the `deploy` directory. The
  `localsearch` backend cannot answer any search without them.
- Only when building with the `opensearch` backend: an OpenSearch instance
  reachable at the URL configured under `ENV.gcme.opensearch` in
  `config/environment.js` (defaults to `http://localhost:9200/_search`).
  You can override this at build time via the `GCME_OPENSEARCH` environment
  variable.

## Setup

Install dependencies from this directory:

```sh
npm install
```

This generates / refreshes `package-lock.json` and installs the Ember CLI 6.12
toolchain along with the dev dependencies needed for linting and testing.

## Search backends

The search UI talks to a service with a two-method API (`executeQuery` and
`complete`). Two services implement it, and the search controller picks one
based on `ENV.gcme.searchBackend`. Everything else about the UI is identical.

### localsearch (default)

`app/services/localsearch.js` answers searches in the browser. On the first
search or autocompletion it asks the corpus service (`app/services/corpus.js`)
for the data: four files are fetched from the site root in parallel, inverted
indexes and sorted completion arrays are built in memory, and every later query
is answered synchronously from those indexes. The reading view reads the same
service, so the download and the index build happen once however they are first
needed.

| File                  | Size | Contents                              |
| --------------------- | ---- | ------------------------------------- |
| `line.json`           | 25M  | Every line of the corpus              |
| `word_dict.json`      | 3.8M | Definitions by word                   |
| `lemma_dict.json`     | 1.9M | Definitions by lemma                  |
| `lemma_tag_dict.json` | 2.8M | Definitions by tagged lemma           |

Notes and limits:

- All four files are fetched together with a 30 second timeout. If any fetch
  fails the error surfaces in the UI and the next search retries the load.
- Once loaded, the data and indexes are cached for the life of the page, so the
  roughly 33M download and the index build happen at most once per page load.
- The files are fetched relative to `rootURL`, which defaults to `/` for
  deployment at a site root. Set `GCME_ROOT_URL=/gcme/` to deploy under a path
  prefix.
- No search server, proxy, or CORS configuration is involved: after the initial
  fetches the app makes no further network requests to search.

### opensearch

`app/services/opensearch.js` POSTs the query DSL to `ENV.gcme.opensearch`. This
requires OpenSearch to be reachable from the browser with the four indices
loaded, which is what `deploy/update_indices.sh` does. Search results come from
the server, so searching downloads only the small static UI files.

The reading view is not affected by this setting: it always reads the corpus
from the static files, so opening the Text tab in an `opensearch` build fetches
`line.json` and the dictionaries just as a `localsearch` build does.

### Configuration

Both settings are read by `config/environment.js` at build time, which means the
chosen backend and endpoint are baked into `dist/`. Rebuild to change them.

| Variable               | Default                            | Effect                                          |
| ---------------------- | ---------------------------------- | ----------------------------------------------- |
| `GCME_ROOT_URL`        | `/`                                | URL path prefix for all assets and data files   |
| `GCME_SEARCH_BACKEND`  | `localsearch`                      | `localsearch` or `opensearch`                    |
| `GCME_OPENSEARCH`      | `http://localhost:9200/_search`    | Endpoint used by the `opensearch` backend only  |

Any other value of `GCME_SEARCH_BACKEND` makes the search page raise
`Invalid search backend: '<value>'. Must be 'opensearch' or 'localsearch'.`

Build with the default local backend, served from a site root:

```sh
npm run build
```

Build for deployment under a path prefix:

```sh
GCME_ROOT_URL=/gcme/ npm run build
```

Build against OpenSearch behind the production `/es` proxy:

```sh
GCME_SEARCH_BACKEND=opensearch GCME_OPENSEARCH=/es npm run build
```

Serve locally against a development OpenSearch instance:

```sh
GCME_SEARCH_BACKEND=opensearch GCME_OPENSEARCH=http://localhost:9200/_search npx ember serve
```

## URLs and bookmarking

The router uses `hash` location: the whole application state lives after the
`#`, as in `https://middleenglish.library.jhu.edu/#/text?group=KnT`.

A search is recorded in the URL, so it can be bookmarked, shared, and revisited
with the browser's history. The URL is written when **Search** is pressed, not
while the form is edited, and paging replaces the current history entry so that
Back leaves the search instead of walking through its pages. Opening such a URL
runs the search and refills the form; the chips show the terms themselves,
without their dictionary definitions.

| Parameter  | Meaning                                    | Default |
| ---------- | ------------------------------------------ | ------- |
| `words`    | Words as spelled in the text               | empty   |
| `lemmas`   | *MED* headwords                            | empty   |
| `tags`     | Tagged headwords                           | empty   |
| `restrict` | Group ids the search is restricted to      | empty   |
| `all`      | Every term must appear in a line           | `false` |
| `sort`     | Sort by location instead of relevance      | `false` |
| `page`     | Page of results, from 1                    | `1`     |
| `size`     | Results per page, clamped to 1–100         | `25`    |

The first four are lists. They are joined with commas, and `%` and `,` inside a
value are escaped as `%25` and `%2C`, because corpus values contain both — the
word dictionary has entries such as `he,` and tagged headwords such as
`mouen@v3%pr_1`. So `?words=god,he%2C` searches for `god` and `he,`. The codec
is `app/utils/query-params.js`.

Every search parameter is declared with `refreshModel: true`, so a change to any
of them re-runs the route's model hook and then the search. The model hook
returns a fresh object each time on purpose: Ember skips setting a route up
again when the resolved model is the same object, and that setup is what runs
the search.

## Reading view

The Text tab (`/text?group=<id>&line=<raw_number>`) shows the corpus as
something to read rather than to search.

- The dropdown offers every group of `text-powersel.json`, from a single tale up
  to a whole author. A text is every line whose group path contains the selected
  id, in the order of `line.json`, which is the order of the printed editions.
- Selecting an intermediate group reads as a sequence of titled sections, one
  heading per group below the selection.
- Every fifth line is numbered with its `raw_number`, as are the first line of
  each section and lines numbered with something other than a number, such as
  the rubrics of the *Astrolabe*. A line that shares its number with an earlier
  one, such as `252a` after `252`, is left unnumbered.
- Clicking a word shows its headword, its tagged headword, the definitions
  recorded for it, how many lines of this text and of the whole corpus contain
  it, and a button which searches for it. The counts are of lines, not of
  occurrences. Untagged words (`not-concorded` in the data) say so.
- The Location column of a search result links to the line it found.

Because a text may be a whole author — 54,113 lines and 429,230 words for
Chaucer — the lines are rendered in chunks the browser may skip while they are
off screen, and the words of a line become separate elements only when the
pointer or the keyboard focus reaches that line. Rendering the whole of Chaucer
takes about two seconds, a single tale under a fifth of a second.

## Development server

Start the Ember CLI development server with live reload:

```sh
npx ember serve
```

The app is then served at <http://localhost:4200>. `ember serve` rebuilds on
every change under `app/` and reports build errors in the terminal. With the
default `localsearch` backend no search server is needed; the data files in
`public/` are served by the development server.

## Linting

Run ESLint (configured in `eslint.config.js` with the Ember Octane rule set)
across `app/`, `tests/`, `config/`, and the root-level `.js` files:

```sh
npm run lint
```

Lint runs with `--max-warnings=0`, so any warning or error fails the command.

## Tests

Run the QUnit test suite (unit, rendering, integration, property-based) via
Ember CLI's test runner:

```sh
npm test
```

This invokes `ember test` and exits non-zero if any test fails.

## Production build

Produce a fingerprinted production bundle in `dist/`:

```sh
npm run build
```

This invokes `ember build --environment=production` and then copies
`dist/index.html` to `dist/404.html`. `dist/` contains the fingerprinted assets
together with everything in `public/`, including the data files the
`localsearch` backend needs. Copy `dist/*` to a static web server.

The router uses `hash` location, so every URL of the application is the single
file `index.html` with the application state after the `#`, as in
`https://host/#/text?group=KnT`. No server rewrite is needed for deep links.
`404.html` remains a copy of `index.html` so that links to the paths the earlier
`history` location produced (`/search`) still reach the application, which then
starts at its default route.

If you built with `GCME_SEARCH_BACKEND=opensearch`, that web server must also
proxy the path given by `GCME_OPENSEARCH` (`/es` in production) to OpenSearch.
