# gcme-ember

The Ember single-page application that powers the public UI of the Glossarial
Concordance to Middle English at <https://middleenglish.library.jhu.edu/>.

This package is built on Ember 6.12 LTS using Octane idioms (native classes,
`@tracked`, Glimmer components, angle-bracket invocation) and the browser-native
`fetch` API. At runtime it consumes the static JSON files generated by
`gcme-tool` (`group-title.json`, `tag-table.json`, `text-powersel.json`).

Searches are answered by one of two interchangeable backends, selected at build
time by `ENV.gcme.searchBackend` in `config/environment.js`:

- **`localsearch` (the default)** answers every search in the browser from the
  static JSON data files, so no search server is needed.
- **`opensearch`** sends queries to the OpenSearch endpoint configured by
  `ENV.gcme.opensearch` (the `/es` proxy in production, an absolute URL such as
  `http://localhost:9200/_search` in development).

See [Search backends](#search-backends) for the tradeoffs and configuration.

## Prerequisites

- **Node.js `>= 20.0.0 < 21.0.0`** is required to install, build, and test this
  package. The `engines.node` field in `package.json` enforces the range, and
  `npm install` will fail with an `EBADENGINE` error on any other version.
- npm 10.x (ships with Node 20).
- The generated data files in `public/`. They are stored in the repository, and
  are refreshed by running `./gen_data.sh` from the `deploy` directory. The
  `localsearch` backend cannot answer any search without them.
- Only when building with the `opensearch` backend: an OpenSearch instance
  reachable at the URL configured under `ENV.gcme.opensearch` in
  `config/environment.js` (defaults to `http://localhost:9200/_search`).
  You can override this at build time via the `GCME_OPENSEARCH` environment
  variable.

## Setup

Install dependencies from this directory:

```sh
npm install
```

This generates / refreshes `package-lock.json` and installs the Ember CLI 6.12
toolchain along with the dev dependencies needed for linting and testing.

## Search backends

The search UI talks to a service with a two-method API (`executeQuery` and
`complete`). Two services implement it, and the search controller picks one
based on `ENV.gcme.searchBackend`. Everything else about the UI is identical.

### localsearch (default)

`app/services/localsearch.js` answers searches in the browser. On the first
search or autocompletion it fetches four data files from the site root in
parallel, builds inverted indexes and sorted completion arrays in memory, and
then answers every later query synchronously from those indexes.

| File                  | Size | Contents                              |
| --------------------- | ---- | ------------------------------------- |
| `line.json`           | 25M  | Every line of the corpus              |
| `word_dict.json`      | 3.8M | Definitions by word                   |
| `lemma_dict.json`     | 1.9M | Definitions by lemma                  |
| `lemma_tag_dict.json` | 2.8M | Definitions by tagged lemma           |

Notes and limits:

- All four files are fetched together with a 30 second timeout. If any fetch
  fails the error surfaces in the UI and the next search retries the load.
- Once loaded, the data and indexes are cached for the life of the page, so the
  roughly 33M download and the index build happen at most once per page load.
- The files are fetched relative to `rootURL`, which defaults to `/gcme/` for
  GitHub Pages deployment. Set `GCME_ROOT_URL=/` to deploy at a site root.
- No search server, proxy, or CORS configuration is involved: after the initial
  fetches the app makes no further network requests to search.

### opensearch

`app/services/opensearch.js` POSTs the query DSL to `ENV.gcme.opensearch`. This
requires OpenSearch to be reachable from the browser with the four indices
loaded, which is what `deploy/update_indices.sh` does. Search results come from
the server, so the browser only downloads the small static UI files.

### Configuration

Both settings are read by `config/environment.js` at build time, which means the
chosen backend and endpoint are baked into `dist/`. Rebuild to change them.

| Variable               | Default                            | Effect                                          |
| ---------------------- | ---------------------------------- | ----------------------------------------------- |
| `GCME_ROOT_URL`        | `/gcme/`                           | URL path prefix for all assets and data files   |
| `GCME_SEARCH_BACKEND`  | `localsearch`                      | `localsearch` or `opensearch`                    |
| `GCME_OPENSEARCH`      | `http://localhost:9200/_search`    | Endpoint used by the `opensearch` backend only  |

Any other value of `GCME_SEARCH_BACKEND` makes the search page raise
`Invalid search backend: '<value>'. Must be 'opensearch' or 'localsearch'.`

Build with the default local backend (for GitHub Pages at `/gcme/`):

```sh
npm run build
```

Build for deployment at a site root (no path prefix):

```sh
GCME_ROOT_URL=/ npm run build
```

Build against OpenSearch behind the production `/es` proxy:

```sh
GCME_SEARCH_BACKEND=opensearch GCME_OPENSEARCH=/es npm run build
```

Serve locally against a development OpenSearch instance:

```sh
GCME_ROOT_URL=/ GCME_SEARCH_BACKEND=opensearch GCME_OPENSEARCH=http://localhost:9200/_search npx ember serve
```

## Development server

Start the Ember CLI development server with live reload:

```sh
npx ember serve
```

The app is then served at <http://localhost:4200>. `ember serve` rebuilds on
every change under `app/` and reports build errors in the terminal. With the
default `localsearch` backend no search server is needed; the data files in
`public/` are served by the development server.

## Linting

Run ESLint (configured in `eslint.config.js` with the Ember Octane rule set)
across `app/`, `tests/`, `config/`, and the root-level `.js` files:

```sh
npm run lint
```

Lint runs with `--max-warnings=0`, so any warning or error fails the command.

## Tests

Run the QUnit test suite (unit, rendering, integration, property-based) via
Ember CLI's test runner:

```sh
npm test
```

This invokes `ember test` and exits non-zero if any test fails.

## Production build

Produce a fingerprinted production bundle in `dist/`:

```sh
npm run build
```

This invokes `ember build --environment=production`. `dist/` contains the
fingerprinted assets together with everything in `public/`, including the data
files the `localsearch` backend needs. Copy `dist/*` to a static web server.

If you built with `GCME_SEARCH_BACKEND=opensearch`, that web server must also
proxy the path given by `GCME_OPENSEARCH` (`/es` in production) to OpenSearch.
