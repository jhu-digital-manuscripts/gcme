# Requirements Document

## Introduction

The `gcme-ember` application is the public-facing UI of the Glossarial Concordance to Middle English at https://middleenglish.library.jhu.edu/. It is currently built on Ember 3.1 (released 2018), runs on Node 4–7+, depends on jQuery via `ember-ajax` and direct `$.ajax` calls, and uses several deprecated build-time addons (`ember-cli-eslint`, `ember-cli-qunit`, `ember-cli-shims`). This feature upgrades the application to Ember 6.12 LTS, requires Node 20, removes jQuery in favor of the native `fetch` API, refreshes all transitive dependencies, and adopts Ember Octane idioms (native classes, tracked properties, Glimmer components, angle-bracket invocation, modern testing).

The upgraded application MUST preserve all existing user-facing behavior of the concordance UI: navigation between About, Search, Tags, Help, and Contact routes; multi-field power-select autocompletion against Elasticsearch (word, lemma, tagged-lemma, and location restriction); paged search execution with “require all words” and “sort by location” toggles; rendering of result tables with column hiding; the tags reference table with grouping; and the ability to consume the static JSON files (`group-title.json`, `tag-table.json`, `text-powersel.json`) generated by the Java tool in `gcme-tool`. Production deployment continues to depend on a web server that proxies `/es` to Elasticsearch.

## Glossary

- **Gcme_Ember_App**: The Ember single-page application at `gcme-ember/` that comprises the user interface.
- **Build_System**: The Ember CLI 6.x toolchain (Embroider/classic build) used to compile, lint, test, and package the Gcme_Ember_App.
- **Elasticsearch_Service**: The Ember service in `app/services/elasticsearch.js` that issues HTTP requests to the configured Elasticsearch search endpoint.
- **Search_Route**: The Ember route at `app/routes/search.js` that loads `text-powersel.json` and `group-title.json` and provides them to the search controller/template.
- **Tags_Route**: The Ember route at `app/routes/tags.js` that loads `tag-table.json` and provides it to the tags controller/template.
- **Search_UI**: The search page (route `search`, controller `search`, template `search.hbs`) and its associated power-select inputs, toggles, action buttons, and result table.
- **Tags_UI**: The tags page (route `tags`, controller `tags`, template `tags.hbs`) and its associated grouped reference table.
- **Static_Data_Files**: The JSON files served from `public/`: `group-title.json`, `tag-table.json`, `text-powersel.json`. These files are produced by `gcme-tool` and are out of scope for modification.
- **Production_Search_Endpoint**: The path `/es` served by the deploy environment, which proxies to Elasticsearch's `_search` API.
- **Test_Suite**: The QUnit-based tests under `gcme-ember/tests/` executed by `ember test`.
- **Project_Documentation**: The repository `README.md` and any per-package README files that describe how to install, build, test, and deploy the Gcme_Ember_App.
- **CI_Configuration**: The repository `.travis.yml` (and any replacement) that runs the build and tests automatically.
- **jQuery**: The JavaScript library currently imported as `$` in the Gcme_Ember_App and pulled in transitively by `ember-ajax`.
- **Fetch_API**: The browser-native `fetch` function used to perform HTTP requests.
- **Ember_Octane**: The Ember programming model based on native ES classes, decorators, tracked properties, Glimmer components (`.gjs` or `.hbs` + class), and angle-bracket invocation.

## Requirements

### Requirement 1: Upgrade to Ember 6.12 LTS

**User Story:** As a developer maintaining the Gcme_Ember_App, I want the application built on Ember 6.12 LTS so that I receive supported security and bug-fix releases and can continue to use the broader Ember ecosystem.

#### Acceptance Criteria

1. THE Gcme_Ember_App SHALL declare `ember-source` in `gcme-ember/package.json` with a semver range that resolves only to versions greater than or equal to 6.12.0 and strictly less than 6.13.0.
2. THE Gcme_Ember_App SHALL declare `ember-cli` in `gcme-ember/package.json` with a semver range that resolves only to versions greater than or equal to 6.12.0 and strictly less than 6.13.0.
3. WHEN `ember --version` is run from `gcme-ember/`, THE Build_System SHALL report an `ember-cli` version greater than or equal to 6.12.0 and strictly less than 6.13.0, and an `ember-source` version greater than or equal to 6.12.0 and strictly less than 6.13.0.
4. WHEN `ember build --environment=production` is run from `gcme-ember/`, THE Build_System SHALL exit with status code 0 within 600 seconds and produce a `dist/` directory that contains an `index.html`, at least one fingerprinted JavaScript asset, at least one fingerprinted CSS asset, and a copy of every file under `gcme-ember/public/`.
5. WHEN `ember build` is run from `gcme-ember/` in development mode, THE Build_System SHALL exit with status code 0 within 600 seconds and emit zero deprecation warnings whose `until` field resolves to a version less than or equal to 6.12.0.
6. IF `ember build` emits a deprecation warning whose `until` field resolves to a version greater than or equal to 7.0.0, THEN THE Gcme_Ember_App SHALL record an entry in `gcme-ember/DEPRECATIONS.md` containing the deprecation `id`, the `until` version, the source location reported by Ember, and a remediation note describing the planned code change.
7. WHEN any developer-facing build, serve, or test command defined in `gcme-ember/package.json` is run on a Node.js runtime whose version does not satisfy the engines range required by Ember 6.12 LTS, THEN THE Build_System SHALL exit with a non-zero status code and emit an error message identifying the unsupported Node.js version and the required range.
8. WHEN `ember serve` is run from `gcme-ember/` in development mode, THE Build_System SHALL within 120 seconds report a successful build and serve the application such that an HTTP GET request to the root path returns status code 200 with the generated `index.html`.

### Requirement 2: Require Node 20

3. IF `npm install` is executed in the `gcme-ember/` directory using a Node.js runtime whose version is `< 20.0.0`, THEN THE Build_System SHALL terminate with a non-zero exit code and emit an `EBADENGINE` engine-mismatch error indicating that Node 20 is required.

### Requirement 3: Remove jQuery from runtime code

**User Story:** As a maintainer, I want jQuery removed from the application so that the bundle is smaller, fewer dependencies need patching, and code aligns with current Ember best practices.

#### Acceptance Criteria

1. THE Gcme_Ember_App SHALL NOT contain any default, named, namespace, side-effect, or CommonJS import of `jquery`, any subpath of `jquery/`, `@ember/jquery`, or `ember-jquery` in any `.js`, `.ts`, `.gjs`, `.gts`, or `.hbs` file under `gcme-ember/app/`, `gcme-ember/tests/`, or `gcme-ember/config/`.
2. THE Gcme_Ember_App SHALL NOT invoke any jQuery API call (including but not limited to `$()`, `jQuery()`, `Ember.$()`, `$.ajax`, `$.get`, `$.post`, `$.getJSON`, and `$.when`) from any module under `gcme-ember/app/` or `gcme-ember/tests/`.
3. THE Gcme_Ember_App SHALL NOT include `jquery`, `@ember/jquery`, or `ember-jquery` under `dependencies`, `devDependencies`, `peerDependencies`, or `optionalDependencies` in `gcme-ember/package.json`.
4. THE Gcme_Ember_App SHALL NOT load jQuery from a `<script>` tag in `gcme-ember/app/index.html` or `gcme-ember/tests/index.html`, where loading is defined as a `src` attribute whose URL contains the case-insensitive substring `jquery`, or any inline script that defines `window.jQuery` or `window.$` as the jQuery library.
5. THE Gcme_Ember_App SHALL NOT register jQuery via `app.import` or any equivalent vendor-import mechanism in `gcme-ember/ember-cli-build.js`.
6. THE Gcme_Ember_App SHALL set `EmberENV.jquery-integration` (or its current equivalent flag) to `false` in `gcme-ember/config/environment.js`.
7. WHEN the Build_System produces JavaScript assets in `dist/` for a production build, THE Build_System SHALL produce assets that do not contain the jQuery library banner string (`jQuery v`) and do not contain the `jQuery.fn.jquery` identifier.
8. IF a third-party Ember addon retained by this upgrade transitively requires `jquery` or `@ember/jquery` according to the resolved dependency graph of `gcme-ember/package.json`, THEN THE Gcme_Ember_App SHALL replace that addon with one whose declared dependencies do not include `jquery` or `@ember/jquery`, OR remove the addon if no module under `gcme-ember/app/` references its exports.

### Requirement 4: Use Fetch_API for HTTP requests

**User Story:** As a developer, I want all HTTP requests issued by the Gcme_Ember_App to use the browser-native Fetch_API so that the application no longer depends on `$.ajax` or `ember-ajax`.

#### Acceptance Criteria

1. WHEN the Elasticsearch_Service executes a search query, THE Elasticsearch_Service SHALL issue an HTTP `POST` to the configured search endpoint using the Fetch_API with `Content-Type: application/json; charset=utf-8` and a JSON-stringified request body, and SHALL abort the request if no response is received within 30 seconds.
2. WHEN an Elasticsearch_Service request returns an HTTP status in the range 200–299 with a response body that parses as valid JSON, THE Elasticsearch_Service SHALL resolve its returned promise with the parsed JSON response body.
3. IF an Elasticsearch_Service request returns an HTTP status outside the range 200–299, THEN THE Elasticsearch_Service SHALL reject its returned promise with an error whose message includes the HTTP status code and status text.
4. IF an Elasticsearch_Service request fails because of a network error reported by the Fetch_API, a request abort, or a response body that cannot be parsed as JSON, THEN THE Elasticsearch_Service SHALL reject its returned promise with an error indicating the failure cause.
5. WHEN the Search_Route loads its model, THE Search_Route SHALL fetch `/text-powersel.json` and `/group-title.json` using the Fetch_API and resolve the route model with the parsed JSON contents of both files only if both fetches return an HTTP status in the range 200–299 with response bodies that parse as valid JSON.
6. WHEN the Tags_Route loads its model, THE Tags_Route SHALL fetch `/tag-table.json` using the Fetch_API and resolve the route model with the parsed JSON contents of that file only if the fetch returns an HTTP status in the range 200–299 with a response body that parses as valid JSON.
7. WHEN the Elasticsearch_Service `complete` method is invoked with a term name and a prefix, THE Elasticsearch_Service SHALL return a promise that resolves to an array of source objects, where each source object includes a `_match` property whose value equals the suggestion text returned by Elasticsearch.
8. IF a Search_Route or Tags_Route fetch fails because of a network error, a request that does not complete within 30 seconds, an HTTP status outside the range 200–299, or a response body that cannot be parsed as valid JSON, THEN THE failing Route SHALL reject its model promise with an error whose message includes the requested URL and the failure cause.
9. IF the Elasticsearch_Service `complete` method receives a successful response that contains no suggestions, THEN THE Elasticsearch_Service SHALL resolve its returned promise with an empty array.
10. THE Gcme_Ember_App SHALL NOT call `$.ajax`, import `ember-ajax`, or import any `ember-ajax/*` subpath from any module under `gcme-ember/app/` or `gcme-ember/tests/`.

### Requirement 6: Adopt Ember_Octane idioms

**User Story:** As a developer, I want the application code to follow Ember_Octane idioms so that the codebase is consistent with current Ember best practices.

#### Acceptance Criteria

1. THE Gcme_Ember_App SHALL define every route, controller, component, service, and helper module located under `gcme-ember/app/` (excluding generated build artifacts and vendored third-party code) using native ES class syntax declared with the `class` keyword and `extends`, and SHALL contain zero occurrences of `Ember.Object.extend(` or `.extend({` in those modules.
2. THE Gcme_Ember_App SHALL declare every instance property whose value drives template re-rendering using the `@tracked` decorator, and SHALL contain zero occurrences of `this.get(` or `this.set(` for reading or writing such properties in modules under `gcme-ember/app/`.
3. THE Gcme_Ember_App SHALL define every reusable UI component under `gcme-ember/app/components/` as a class that extends the Glimmer component base from `@glimmer/component`, with its template file co-located in the same directory as the component class file and sharing the same base filename, except for template-only components that have no backing class.
4. THE Gcme_Ember_App SHALL invoke every component declared inside `gcme-ember/app/` from `.hbs` templates using angle-bracket syntax (e.g. `<MyComponent />`), and WHERE a component is provided by a third-party addon listed in `gcme-ember/package.json` that does not support angle-bracket invocation, THE Gcme_Ember_App SHALL document that exception in a comment adjacent to the curly invocation identifying the addon name.
5. THE Gcme_Ember_App SHALL replace every `{{action ...}}` modifier in `.hbs` templates under `gcme-ember/app/` with an `{{on "<eventName>" this.<handler>}}` modifier whose handler method is decorated with `@action` on the backing class, and SHALL contain zero occurrences of the `{{action ...}}` modifier in those templates.
6. THE Gcme_Ember_App SHALL replace every `{{link-to ...}}` block-form and inline-form invocation in `.hbs` templates under `gcme-ember/app/` with an equivalent `<LinkTo @route=... />` angle-bracket invocation that targets the same route and passes the same models and query parameters.
7. THE Gcme_Ember_App SHALL replace every `Ember.computed(...)` or `computed(...)` decorator in modules under `gcme-ember/app/` with a native ES getter whose dependent values are declared as `@tracked` properties or accessed from `@tracked` sources, and SHALL contain zero imports of `computed` from `@ember/object` in those modules.
8. WHERE the existing search functionality is implemented as a controller class that holds UI state, THE Gcme_Ember_App SHALL relocate that state and behavior into a single Octane-idiomatic destination, choosing either (a) a controller class that uses `@tracked` properties and `@action` methods with no `Ember.Object.extend` and no `this.get`/`this.set`, or (b) a Glimmer component invoked from the route template, such that the chosen destination contains all search UI state previously held by the controller.
9. WHEN the developer runs `eslint` against `gcme-ember/app/` and `gcme-ember/tests/` with the project's lint configuration enabling `eslint-plugin-ember` recommended rules together with the `ember/no-classic-classes`, `ember/no-classic-components`, and `ember/no-jquery` rules at error level, THE Gcme_Ember_App SHALL produce zero errors and zero warnings under `--max-warnings=0`.
10. WHEN the existing automated test suite for `gcme-ember` is executed after the Octane refactor, THE Gcme_Ember_App SHALL pass every test that passed before the refactor without modification to test expectations covering user-observable behavior.
11. IF any module under `gcme-ember/app/` cannot be converted to an Octane idiom because of a third-party dependency constraint, THEN THE Gcme_Ember_App SHALL retain the classic implementation only for that module and SHALL include an inline comment naming the blocking dependency and the specific idiom it prevents.

### Requirement 7: Preserve existing user-facing functionality

**User Story:** As a user of the Glossarial Concordance, I want every feature available before the upgrade to remain available after the upgrade so that my research workflow is uninterrupted.

#### Acceptance Criteria

1. THE Gcme_Ember_App SHALL render a top navigation bar containing links labeled "About", "Search", "Tags", "How To Guide", and "Contact" on every routable page of the application (including the `search`, `tags`, `about`, `how-to-guide`, and `contact` routes), matching the labels listed in `app/templates/application.hbs` before the upgrade.
2. WHEN a user navigates to the application root URL, THE Gcme_Ember_App SHALL redirect to the `search` route within 2 seconds.
3. WHEN a user types into the "Middle English word(s)" input on the Search_UI, THE Search_UI SHALL display autocomplete suggestions returned by the Elasticsearch_Service for the `word` field, beginning at one or more characters of input and showing at most ten suggestions per query.
4. WHEN a user types into the "Middle English Dictionary headword(s)" input on the Search_UI, THE Search_UI SHALL display autocomplete suggestions returned by the Elasticsearch_Service for the `lemma` field, beginning at one or more characters of input and showing at most ten suggestions per query.
5. WHEN a user types into the "Middle English word (by part of speech)" input on the Search_UI, THE Search_UI SHALL display autocomplete suggestions returned by the Elasticsearch_Service for the `lemma_tag` field, beginning at one or more characters of input and showing at most ten suggestions per query.
6. WHEN a user submits a search with at least one selected word, lemma, or tagged lemma, THE Search_UI SHALL display a paged table of matching lines whose page size is configurable by the controller's `pageSize` value with a default of 25 and bounds between 1 and 100, whose initial page is page 1, and whose initial result offset is 0.
7. WHEN the "All words and headwords must be present in a line" checkbox is selected at the time of search submission, THE Search_UI SHALL submit an Elasticsearch query whose boolean clause is a conjunction (`must`) of the selected term clauses.
8. WHEN the "All words and headwords must be present in a line" checkbox is not selected at the time of search submission, THE Search_UI SHALL submit an Elasticsearch query whose boolean clause is a disjunction (`should`) of the selected term clauses.
9. WHEN the "Sort results by location instead of relevance" checkbox is selected at the time of search submission, THE Search_UI SHALL submit an Elasticsearch query whose `sort` parameter orders results by `id` ascending, then `number` ascending, then `raw_number` ascending.
10. WHEN the user selects one or more entries in the "Restrict to location" input at the time of search submission, THE Search_UI SHALL submit an Elasticsearch query whose `query.bool.filter.terms.group` array contains the `id` of each selected restriction.
11. WHEN the user clicks "Next" on a results page that is not the last page, THE Search_UI SHALL request and display the next page using the same query parameters and an updated `from` offset equal to `(pageNumber - 1) * pageSize`, AND IF the displayed page is the last page, THEN THE Search_UI SHALL disable or hide the "Next" control so that no request is issued beyond the final page.
12. WHEN the user clicks "Previous" on a results page that is not the first page, THE Search_UI SHALL request and display the previous page using the same query parameters and an updated `from` offset equal to `(pageNumber - 1) * pageSize`, AND IF the displayed page is page 1, THEN THE Search_UI SHALL disable or hide the "Previous" control so that no request is issued before page 1.
13. WHEN the user clicks "Clear" on the Search_UI, THE Search_UI SHALL reset the selected words, lemmas, tagged lemmas, location restriction, current result, and page number to their initial empty state.
14. WHEN a search returns zero hits, THE Search_UI SHALL within 2 seconds display the text "No matches" in place of the results table and SHALL NOT display pagination controls.
15. WHEN the user navigates to the Tags_UI, THE Tags_UI SHALL render a grouped reference table whose rows are loaded from `/tag-table.json` and whose grouping property is `group`.
16. WHEN the user views a search result row, THE Search_UI SHALL display a "Location" column whose value is composed of the row's top-level group title and its most specific group title from `group-title.json`, a "Line number" column populated from `_source.raw_number`, and a "Text" column populated from the highlighted `text` field when present and from `_source.text` otherwise.
17. IF the user activates the search submit control while no word, lemma, or tagged lemma is selected, THEN THE Search_UI SHALL NOT issue a query to the Elasticsearch_Service and SHALL display an indication that at least one search term is required, leaving the previously displayed results and page number unchanged.
18. IF the Elasticsearch_Service returns an error response or is unreachable during a search submission, page navigation, or autocomplete request, THEN THE Search_UI SHALL display an indication that the search service is unavailable, SHALL NOT replace the previously displayed results with partial or empty data, and SHALL preserve the user's selected words, lemmas, tagged lemmas, location restriction, and page number.
19. IF the request for `/tag-table.json` fails or returns a non-success response, THEN THE Tags_UI SHALL display an indication that the tag reference table could not be loaded in place of the grouped reference table.

### Requirement 8: Preserve Elasticsearch endpoint configuration

**User Story:** As an operator, I want the deployment configuration for the search endpoint to be the same as before so that no production infrastructure changes are needed.

#### Acceptance Criteria

1. WHILE the application is running with `EmberENV.environment` equal to `production`, THE Gcme_Ember_App SHALL issue every search request to the path `/es` resolved relative to the page origin (`window.location.origin`), with no scheme or host prefix added by the client.
2. WHILE the application is running with `EmberENV.environment` equal to `development` or `test`, THE Gcme_Ember_App SHALL issue every search request to the absolute URL read from `ENV.gcme.elasticsearch` in `config/environment.js`, using that value verbatim without modification, trimming, or fallback substitution.
3. THE Gcme_Ember_App SHALL read the search endpoint exclusively from the `ENV.gcme.elasticsearch` configuration key in `config/environment.js`, and SHALL NOT define, reference, or fall back to any alternate configuration key, hard-coded URL, or environment variable for the search endpoint.
4. IF `ENV.gcme.elasticsearch` is undefined, empty, or not a syntactically valid URL while the application is running in the `development` or `test` environment, THEN THE Gcme_Ember_App SHALL abort the search request, SHALL NOT issue any network call, and SHALL surface an error to the caller indicating that the Elasticsearch endpoint configuration is missing or invalid.

### Requirement 10: Update build, lint, and CI tooling

#### Acceptance Criteria

1. THE Gcme_Ember_App SHALL define an `npm run lint` script in `gcme-ember/package.json` that runs ESLint over `app/`, `tests/`, `config/`, and root-level `.js` files.
2. WHEN `npm run lint` is run from `gcme-ember/` and ESLint reports any error-level or warning-level finding, THE Build_System SHALL exit with a non-zero status code; otherwise THE Build_System SHALL exit with status code 0.
3. THE Gcme_Ember_App SHALL define an `npm run build` script in `gcme-ember/package.json` that runs `ember build --environment=production` and exits with a non-zero status code if the build fails.
4. THE Gcme_Ember_App SHALL define an `npm test` script in `gcme-ember/package.json` that runs `ember test` and exits with a non-zero status code if any test fails.
5. WHEN a push is made to the repository or a pull request is opened or updated, THE CI_Configuration SHALL install the latest Node.js 20.x LTS patch release, then run, in this order, `npm ci` if `gcme-ember/package-lock.json` is present (`npm install` otherwise), `npm run lint`, `npm test`, and `npm run build` from `gcme-ember/`.
6. IF any step executed under acceptance criterion 5 terminates with a non-zero status code, THEN THE CI_Configuration SHALL mark the CI job as failed and SHALL NOT execute subsequent steps in that job.
7. THE Project_Documentation SHALL document the commands `npm install`, `npm run lint`, `npm test`, and `npm run build` in `gcme-ember/README.md` (creating the file if it does not exist).
8. THE Project_Documentation SHALL update the deployment instructions in the repository `README.md` to refer to Node.js 20.x and to the commands listed in acceptance criterion 7 instead of the previous Node 10 and `ember build` instructions.
